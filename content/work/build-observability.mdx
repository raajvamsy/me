## The problem

Builds fail for many reasons: a platform bug, a mistake in a project, or infrastructure. Nobody could tell which ones mattered, because the signal was buried in log lines.

## First, make the numbers true

My first dashboard was confidently wrong. Log lines could arrive more than once, and it counted them as new builds. I rebuilt the pipeline around when each line was written, with one record per real build, and checked the result against the source until the two matched exactly.

This shaped everything after it. A dashboard you can't trust is worse than none.

## Turning logs into owned errors

Each failure is normalised into a stable error code, so one problem with many variations appears once, and different problems don't share a code. Each code is attributed to the side that can fix it.

## The AI investigator

An agent runs on a schedule or on demand. It picks the top errors, reads the logs and writes a root-cause report for each. Each schedule has its own playbook, and findings are routed to the right people.

## Asking questions in plain English

Build data is exposed through an MCP server. The assistant has to follow a procedure: frame the window, count, check known issues, read logs if needed, then check that the numbers add up before answering.

## Honest status

The investigator has produced findings, but I don't yet have evidence that it reduces time to fix. That is the next thing to measure.
