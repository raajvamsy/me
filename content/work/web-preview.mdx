## The problem

Preview is the loop developers wait on all day. One memory-limited container serves several users at once, which rules out a persistent dev server for each project.

The first version of the new pipeline didn't fit. A single build could be killed by the kernel for running out of memory, and that surfaced only as a bare `SIGKILL` in the logs. Measuring it showed memory was the binding limit, not CPU, and that the spike wasn't where I had assumed.

## What changed

- **A shared transform cache.** Metro's transform cache became shared across projects, so work done for one can be reused by another.
- **A build admission lock.** Different projects previewing at once now queue, and no longer run each other out of memory.
- **Boundary-based edit builds.** With caches in place, an edit walks far fewer modules.
- **A faster live-reload client.** The time to apply a new build dropped sharply.

## Results

| Measure | Improvement |
|---|---:|
| Repeat build, same project | 7× faster |
| Peak memory | Nearly half |
| Live reload | 3.5× faster |

The build comparison is a cold shared cache against a warm one on the same project. It shows what the cache buys, and it isn't a comparison of the whole new pipeline against the old one.

## What I learned

Measure before optimising. The bundler looked like the problem, but the memory ceiling was elsewhere, so tuning the bundler alone wouldn't have fixed it.
